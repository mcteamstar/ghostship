# Comp/comps terminology compatibility matrix

Research snapshot: 2026-11-15. User decision: `comp`/`comps` is canonical across Ghostship's interfaces, configuration, persisted records, documentation, and implementation names. `composition`/`compositions` remains only as a compatibility alias at boundaries. This matrix records the pre-implementation inventory and recommendations; implementation progress is tracked in tasks 4.1–4.8.

## Framework and consumer evidence

- `transport/requirements.txt` pins `mcp[cli]==2.2.0`.
- Tool input schemas are generated from the Python callable signature; the current tool is registered by function name using `mcp_instance.tool()(launch)`, so parameter aliases belong in the `launch` signature. Registering another launch function under a different name would expose a second public tool, not an argument alias. [Pinned SDK tool registration](https://github.com/modelcontextprotocol/python-sdk/blob/9972c21aa42054fb1450c5fc614761ed11847ec6/src/mcp/server/mcpserver/server.py)
- Resource reads are addressed by URI. Pinned SDK v2.2.0 creates a resource for each explicit URI passed to `resource(uri, ...)` and stores static resources keyed by URI, confirming that two URIs can share one handler. The implementation phase should still verify both entries appear in `resources/list` and read identically.
- The live `carrier` MCP connection currently advertises `launch` with `composition` and exposes `transport://compositions`; the resource is visible in resource discovery. This confirms the deployed public contract matches the repo's current registration.
- Repo source, tests, skills, and specs demonstrate known compatibility contracts, but do not enumerate every external client. The implementation phase should inspect any deployed MCP client configuration and API consumers before setting a deprecation date.

## Recommended staged implementation

1. Add `comp` as the canonical `launch` input; retain `composition`. When both are supplied, `comp` wins (warn on conflict), and retain the current default after alias resolution.
2. Register `transport://comps` and keep `transport://compositions` as an alias to the same handler. Update the resource description/content and launch documentation to use “comps.”
3. Make `comps` the authored `crews/registry.json` key and loader source of truth; accept legacy `compositions`. If both keys are present with different values, `comps` wins and the loader logs a warning.
4. Make `comp` canonical in persisted crew records and both MCP/REST responses. Read legacy `composition` records; emit both fields during rollback compatibility. Update Radar to use `comp` and display “Comp.”
5. Rename internal implementation symbols and update repo-local specs, tests, docs, and the installer example. Reconcile the stale `crew-types` spec with actual behavior. Set any eventual deprecation/removal policy only after client usage is known.

Rollback: keep old launch input, resource URI, registry key, and crew record/API field operational throughout the compatibility window. Persist both record fields before any rollback to code that only reads `composition`. Revert canonical labels/new aliases without discarding either value. A future breaking removal would require separate approval and evidence of client migration.
