## Context

The existing app groups running and inactive crews, polls for fleet state and fetches per-crew snapshots on expansion. Corsair returned 24 stopped crews during discovery, so an all-stopped fleet is a normal operator state. Source inspection found two pressure points: the mobile CSS clips the only Last Task control, and each expanded row stacks tasks, Captain, credentials and eight mailbox sections in the same scrolling surface as the fleet. The current hooks already preserve data across polls and provide independent failure states.

## Goals / Non-Goals

- Make it easy to scan the fleet, find an exception, and open a crew without losing list context.
- Preserve familiar Ghostship terminology, the serif display identity and both system themes. Use restrained accents and readable data typography. Keep warnings visible in text.
- Keep existing fleet and action APIs. Add a read-only metadata endpoint for mailbox history. The inspector shows task and mailbox snapshots while fleet state continues to poll.

## Decisions

1. **Fleet signal first.** Put Ghostship Radar, running and stopped counts, capacity and available memory (when reported), and freshness in a full-width shared header. Do not show the one-item Fleet sidebar. Place search, All / Running / Inactive / Needs attention filters and a labeled sort control above the rows. Default to All and newest created first. Last Task offers both directions within the existing groups. Search by crew ID or comp within the current status filter. Needs attention means an explicitly unhealthy gateway on a running crew or a stale enabled Captain using the existing rule. A stopped crew alone is routine. A zero-match state offers a clear-filters action.
2. **Responsive workspace.** Let operators toggle between a dense list and cards at every fleet width. Both use the same result set, filters, sort and selection. On phones use compact stacked list rows and single-column cards. Show crew ID, status, gateway warnings, active task count and available actions. Keep secondary fields reachable in Overview. Open dashboard and Copy ID do not select a crew. Use a full-width fleet until two panes fit, targeting 1100 CSS pixels. On wide screens, selection opens an adjacent inspector with its own scrolling region. Below that threshold, selection shows a full-width inspector with a visible Back to fleet control. Below 640 pixels, crew summaries prioritize name, status, activity and warnings. Backend, comp and timing fields remain reachable in the inspector. Keep search and sort visible whenever the list is shown.
3. **Unified inspector.** Keep crew identity, status, dashboard and copy actions with the overview at the top of one inspector. Show mailbox history in the body below the overview. Default to newest-first history grouped by local date. Sender and Recipient group the same records by sender and receiving mailbox respectively, with newest first inside each group. Render wrapping subjects and clearly label unavailable timestamps or sender names. Group long sections with headings and make finished tasks collapsible. Label stopped crew creation time separately from uptime. Keep unavailable and empty states distinct. Refresh auth remains an explicit action with its current outcome guidance. On wide screens, keep the overview and message body independently scrollable. On narrow screens, stack them in one page flow.
4. **Selection and history.** The existing hash identifies one selected crew and supports direct entry. Browser Back and Forward restore selection. On narrow screens, move focus to the inspector heading on entry and restore it to the invoking crew when returning, or the filter when that crew is unavailable. Keep filter, sort and list scroll through selection and polling. If filters hide a selected crew on wide screens, keep its inspector open with an indication that it is outside the results. If the crew disappears from the fleet, clear selection and explain why. In-flight reads from a previous selection must never populate the current inspector. A pending credential refresh remains associated with its crew through selection changes and must not trigger a duplicate POST.

5. **Mailbox contract.** Add a same-origin, read-only crew history route through Radar and the existing authenticated internal transport boundary. Return a bounded snapshot of retained deliveries with subject, normalized sender when available, receiving mailbox as recipient, and a parsed timestamp when available. Use mailbox provenance for recipient, preserve repeated deliveries, and order ties consistently. Put undated deliveries after dated ones. Display a no-subject label for missing subjects and indicate when the snapshot is capped. Treat header values as plain text and keep bodies and attachments outside the response. Preserve the current stopped-crew read behavior and the distinction between unavailable and empty.

6. **Freshness during outages.** Keep the last successful refresh time beside the error and show a text label at the existing stale and critically stale thresholds. A first-load failure shows no fabricated timestamp. Announce meaningful error or severity transitions through a live region without announcing each successful poll.
7. **Load history with the selected crew.** Request history when the operator opens a crew inspector. Do not request history for unselected crews. Keep the result while the crew remains selected and the fleet polls. Cancel pending reads when the crew changes or closes. Ignore late results and make a failed read retryable from the message body. Returning to a previously closed inspector starts a fresh snapshot.

## Risks / Trade-offs

A single inspector gives the fleet a stable layout and trades away simultaneous expanded rows. Preserve quick crew switching on wide screens and list position on narrow screens. Use stopped, mixed and degraded fleet fixtures because the live Corsair snapshot only covered stopped crews. Check focus, wrapping and contrast in a real browser in both themes.

## Migration Plan

Deliver as a frontend update using the existing build and portal. Preserve current crew hash links. Deploy the matching Radar and transport versions together. No mailbox migration is needed.
