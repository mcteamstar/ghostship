# Design

## Context

The spec-ops image pins OpenSpec 1.14.3. Its six core Academy OpenSpec skills were generated by 1.14.3, while `AcademyLoader` stages skills into shared `.agents/skills/` and runs the baked `.agents/setup` to wire them into detected backends. The optional `openspec-verify-change` skill is also required for the planned hygiene Captain order. The repo's OpenSpec configuration does not configure delivery targets, so `openspec update` at the repo root does not refresh those Academy assets. See proposal.md for motivation and the specs for required behavior.

## Goals / Non-Goals

**Goals:**
- Ship OpenSpec CLI 2.1.0 with its matching six core workflow skills and the optional `openspec-verify-change` skill.
- Preserve the current Academy delivery path and persona workflow ownership.
- Make backend invocation, unavailable optional skills, dependency evidence, and fresh-crew verification explicit.

**Non-Goals:**
- Migrate Executor's host CLI, global skills, or wrapper commands.
- Bundle every optional OpenSpec workflow skill. `openspec-verify-change` is included because the planned hygiene Captain order depends on it; optional workflows such as `continue` remain unbundled.
- Run a migration against crew user projects or delete user-owned command files as part of image construction.

## Decisions

1. **Pin OpenSpec 2.1.0 and treat its generated skills as a coupled asset.** Update the spec-ops image's exact npm pin and refresh all six Academy skill files from the v2 CLI's shared `.agents/skills/` output. Keep Academy as the single Ghostship-owned source that `AcademyLoader` stages. Do not rely on running `openspec update` in the Ghostship repository: it has no delivery configuration, and the checked dry run produced no updates. Generate and inspect candidate assets in a disposable fixture, then adapt only Ghostship-specific front matter or policy text while retaining the upstream v2 workflow content.

   **Alternative considered:** Install skills into each backend separately. This duplicates skill sources and conflicts with the current `.agents/setup` shared-delivery architecture.

   Bundle `openspec-verify-change` as the one selected optional workflow skill, alongside the six core skills. Verify its source and compatibility with OpenSpec 2.1.0 instead of assuming it is part of the core generated set. This gives the planned hygiene Captain order a versioned, crew-delivered verification workflow without expanding the bundle to every optional skill.

2. **Keep the six existing OpenSpec persona roles and update invocation examples per backend.** Agent prompts continue to describe the established Ghost/Spectre/Banshee/Reaper workflow ownership. Refer to installed skill names using `$openspec-*` for Codex and `/openspec-*` only for backends that support slash skill invocation. Remove references that imply OpenSpec-generated `/opsx:*` commands remain available; keep Executor-owned wrappers out of this migration.

   **Alternative considered:** Add a new technical persona-to-skill restriction. Skills are crew-wide today and the existing persona contract is prompt-level; changing that access model is unrelated to the CLI migration.

3. **Document `continue` as an optional workflow with an instructions-command fallback.** Keep `openspec-continue-change` unbundled. When that skill is absent, direct agents to query `openspec instructions` for the next artifact and follow the returned requirements, with the repository root selected from the target project. This is separate from `openspec-verify-change`, which is intentionally bundled for the hygiene Captain order.

   **Alternative considered:** Bundle every optional workflow. That expands Academy scope and can create duplicate or unsupported skill variants without being required for the current six-role workflow.

4. **Do not run the migration against crew project data during build or launch.** Review v2 migration output on disposable fixtures that represent legacy generated command files and an existing OpenSpec change. Verify the new CLI can inspect the existing change and that files remain untouched unless a reviewed migration explicitly targets them. Fresh-crew checks validate skill discovery and workflow instructions across the supported backend setup.

   **Alternative considered:** Automatically run the migration for every project. This risks modifying user-owned files at crew startup and makes image upgrades destructive.

5. **Record the CLI and skills as a coupled dependency review.** Update `config/dependencies.yaml` and dated evidence with the exact CLI version, source of generated skills, migration inspection, image build result, and fresh-crew checks. Record unknown runtime/backend coverage as unknown rather than treating image build success as proof of model generation compatibility.

## Risks / Trade-offs

- [Upstream v2 skill output may differ from Ghostship's six skill names or persona assumptions] → Generate in a disposable fixture first, compare the full set and workflow contracts, and resolve mismatches before replacing Academy assets.
- [Some backends may not discover `.agents/skills/` or may use different invocation syntax] → Verify actual setup output and skill discovery in fresh crews; document invocation syntax by backend.
- [The v2 CLI may interpret existing artifacts differently] → Inspect and exercise a representative existing change using a disposable copy; do not apply migration output to operator project files automatically.
- [OpenSpec version 2.1.0 may not match maintainers' local 2.0.0 installation] → Pin and verify the bundled CLI and generated metadata together; document the bundle's exact version rather than implying all maintainers share it.

## Migration Plan

1. Produce and inspect v2.1.0 migration and skill output in disposable fixtures before changing Academy assets.
2. Update the CLI pin, six core Academy skills, optional verify skill, persona prompts, Academy documentation, dependency inventory, and dated review evidence together.
3. Build the spec-ops image and launch a fresh crew; check CLI version, skill discovery, per-backend invocation guidance, and the optional `continue` fallback.
4. Open an existing-change fixture with the upgraded CLI and confirm its artifacts remain readable and usable; retain migration output for review without applying it to real crew projects.
5. If verification fails, revert the CLI and skill bundle together and retain the existing crew image until corrected.

## Open Questions

None. The target is OpenSpec 2.1.0, selected as the current v2 release during research.
